# 性能剖析与优化（v1.1）

本文记录 v1.0 的性能瓶颈是怎么测出来的、v1.1 做了哪些优化、效果如何，以及还剩哪些可做的事。

- 复现：`cargo run --release -p geoverse-precise-core --example profile`（核心层）、`node bench/profile.mjs`（JS ↔ WASM 层）
- 环境：Node 22，wasm32 release（wasm-opt -O3），同一台机器，数值为多次运行平均

---

## 1. 瓶颈在哪里

先把耗时拆成三层来测：**原生算法**、**WASM 边界**、**JSON 序列化**。

### 1.1 原生算法（v1.0）

| 项目 | 耗时 |
|---|---|
| 大地线反算（距离） | 1.00 µs |
| 大地线正算（目标点） | 0.36 µs |
| 横轴墨卡托正算 | 0.43 µs |
| `nearest_point_on_line`（280 段线，单次查询） | **2.10 ms** |
| 缓冲区：1100 km 线，planar 边 | 10.2 ms（构件 4.5 + 合并 3.7） |
| 叠加：两个 220 顶点面相交 | 0.97 ms（其中 i_overlay 本身只占 0.018 ms） |

两个结论：

1. **最近点查询慢了两个数量级**。每段线都跑一次 Karney 截距迭代（每次约 10 轮，每轮 3 次心射投影 + 1 次反投影），280 段就是上万次大地线求解。
2. **叠加的时间几乎全花在投影上**，布尔运算本身只占 2%。

### 1.2 WASM 边界与 JSON（v1.0）

| 项目 | 耗时 |
|---|---|
| 无参数调用 | 0.40 µs |
| `distance`（4 个数 + 2 个字符串参数） | 1.21 µs |
| 1 万顶点面：JS 侧 `JSON.stringify` | 3.2 ms |
| 同上：Rust 侧解析 + 计算 | 5.9 ms |
| **2 万点逐个 `booleanPointInPolygon`（500 顶点面）** | **5.46 s** |
| 200 次 `pointToLineDistance`（280 段线） | 2.08 s |

最刺眼的一条：每次点在面内判断都要把同一个 19 KB 的面重新序列化、重新解析、重新扫描——**单次 273 µs，其中真正的几何计算不到 1 µs**。

## 2. 做了哪些优化

### 2.1 预处理几何 + 空间索引（影响最大）

新增 `Prepared` / `PreparedGeometry`：几何只解析一次，在 WASM 内存里保留 `geo` 几何、分段累计长度和一张**经纬度均匀网格索引**。

- 点在面内：只扫描查询点所在网格行的线段做射线法；
- 最近点：按单元格到查询点的距离**最近优先**遍历，配合下面的候选筛选；
- 配套批量接口 `containsMany` / `nearestMany` / `distanceMany` / `within`，一次调用处理整个 `Float64Array`。

### 2.2 最近点查询：先粗筛，再精算

原来每段线都精算。现在分两步：

1. **球面粗筛**：把点和线段端点转成单位向量，用叉积/点积算大圆弧距离（约 60 ns/段，只有符号判断和一次 `asin`），并用**查询点纬度处的高斯曲率半径**代替平均球半径，把球面与椭球的偏差从 0.55% 压到 0.1% 量级；
2. **带界精算**：按粗筛距离排序，先精算最优候选，再用它的精确距离作上界剪枝；粗筛得到的球面垂足直接作为迭代初值，收敛通常只需 1～2 轮。

另外把"沿线里程"（`location`）改成按需计算——它需要把前面每一段的长度加起来，单独占 90 µs。

### 2.3 横轴墨卡托改用 Clenshaw 递推

Krüger 六阶级数原来逐项调用 `sin/cos/sinh/cosh`（每次 24 个超越函数）。改成复数参数的 Clenshaw 递推后只需 1 组 `sin/cos` + 1 组 `sinh/cosh`，正反算精度不变（与 PROJ 对照仍为纳米级）。

### 2.4 平面边的长度与面积：闭式积分代替加密

`edges: 'planar'`（默认）原先要把长边切成几十段才能按大地线算。现在直接积分：

- 长度：对椭球线元 `ds = √((M dφ)² + (N cosφ dλ)²)` 做 7 点高斯-勒让德积分；
- 面积：用"赤道到纬度 φ 之间、每弧度经度的面积" `Q(φ)` 的闭式解，沿边积分 `∮ Q(φ) dλ`。

结果与"极细加密后按大地线计算"在 1e-9 相对误差内一致（有单测），而且**不再有加密误差**，速度快 4～6 倍。

### 2.5 缓冲区：合并亚容差折点

输入是大地线采样的轨迹时，按经纬度直线解释会在每个折点产生极小的转角。原来每个转角都生成一个独立的扇形——成千上万个近似退化的小多边形，合并阶段被这些碎片拖慢。

现在：当折点两侧法线张开的间隙小于 `tolerance` 时，两侧条带共用**平均方位角**的法线，不再生成扇形。几何上等价（偏差小于容差），构件数减半。

## 3. 效果

### 3.1 JS 层（用户实际调用）

| 场景 | v1.0 | v1.1 | 提升 |
|---|---|---|---|
| 2 万点在面内（500 顶点面） | 5456 ms | **0.17 ms**（批量） | **约 32000×** |
| 同上，逐次调用预处理几何 | 5456 ms | 1.69 ms | 3200× |
| `pointToLineDistance`（280 段线，含 JSON） | 10.4 ms | **0.63 ms** | 16.5× |
| 面积（100 顶点，planar） | 339 µs | **73 µs** | 4.6× |
| 面积（1 万顶点） | 12.4 ms | 7.5 ms | 1.7× |
| `transformCoords` 2 万点 | 12.7 ms | **6.7 ms** | 1.9× |
| 20 万点投影（对比 proj4js 1826 ms） | 94 ms | **67 ms** | 对 proj4js 27× |
| 缓冲区：1100 km 线（大地线边） | 7.9 ms | 5.1 ms | 1.5× |
| 缓冲区：550 km 面（大地线边） | 7.0 ms | 6.2 ms | 1.1× |

### 3.2 核心层

| 项目 | v1.0 | v1.1 |
|---|---|---|
| `nearest_point_on_line`（280 段，不含里程） | 2100 µs | **58 µs** |
| 同上，带索引且点靠近线 | – | **25 µs** |
| 横轴墨卡托正算 | 0.43 µs | **0.27 µs** |

## 4. 还能怎么优化

按投入产出排序：

1. **大几何的 JSON 仍是主要开销**。1 万顶点面求面积 7.5 ms 中，`JSON.stringify` 3.2 ms、Rust 侧解析约 2.5 ms，真正计算不到 1.5 ms。
   下一步：给 `Prepared` 补上 `area()` / `length()` / `buffer()` 等方法复用已解析几何；再进一步可以引入二进制几何通道（坐标走 `Float64Array` + 结构描述），跳过 JSON。
2. **单次大地线反算 0.85 µs 是测量密集场景的地板**。可以提供 `precision: 'fast'` 选项，在几十公里内用局部曲率半径的解析解（毫米级误差、约 0.1 µs），把批量距离再快 5～8 倍。
3. **缓冲区构件生成**是大范围缓冲的主要耗时（planar 边约占 70%）。可以改成 JTS 式"单条原始偏移环 + 非零环绕"，把合并阶段的轮廓数从上千降到个位数；预估整体再快 2～3 倍，但需要重新验证退化情形。
4. **体积**：当前 wasm 1.34 MB（gzip 498 KB）。按函数名归类的构成：Rust 核心/格式化 32%、geoverse-precise 自身 20%、i_overlay 11%、geo 算法 8%、GeoJSON 解析 7%、serde_json 4.5%、DE-9IM 4%、rstar 4%。
   可做：给 `relate` / 凹包 / 拓扑检查加 cargo feature 开关，按需构建；用 `panic_immediate_abort` 构建（可再省 20%～30%，需 nightly）；或把 wasm 放到 Worker 里懒加载。
5. **多线程**：批量接口天然可并行，wasm threads（SharedArrayBuffer + rayon）在有 COOP/COEP 头的站点可以再快 3～4 倍。
6. **Web Worker 封装**：大范围缓冲、叠加、拓扑检查都是几十毫秒级，放进 Worker 可以避免卡住主线程交互。

## 5. v1.2 新增函数的代价

这一轮补的函数大多是"算一次、看结果"的分析型调用，不在热路径上，所以取舍偏向正确性。
几处刻意的权衡：

| 函数 | 做法 | 代价 |
|---|---|---|
| `isobands` | 三角形裁剪后用整数内核并集 | 一次布尔运算换来 band 之间无缝无叠；格网越大越贵，10⁴ 量级单元仍在几十毫秒 |
| `voronoi` | 每个站点对其 Delaunay 邻居做半平面裁剪 | 邻居数是常数量级，整体线性；只有越出 bbox 的单元才走一次布尔裁剪（内部单元跳过） |
| `moranIndex` / `distanceWeight` | 稠密 n×n 权重矩阵 | 与 turf 一致的接口语义，n 上千就不合适；真要大规模应改成邻接表 |
| `shortestPath` | A* + string pulling | 拉紧阶段最坏是 O(路径长度²) 次相交测试，已按 512 个顶点限制前瞻 |
| `clustersDbscan` | 局部平面上的均匀桶索引 | 半径查询接近常数时间，不退化成 O(n²) |
| `geojsonRbush` | 均匀网格 + 懒重建 | `insert` 只标记失效；极端不均匀分布下逊于真正的 R 树 |

产物体积：未经 `wasm-opt` 的模块 2.04 MB，gzip 后 668 KB（v1.1 经 `wasm-opt -O3` 是 1.34 MB /
gzip 498 KB，同口径下本轮约 +25%，新增的 `spade` Delaunay / CDT 内核占大头）。
按 cargo feature 拆分（把插值、聚类、统计做成可选）留给 v1.3。

> 本轮的沙箱环境只有 binaryen 108，它会把 externref 表重编号而不修正指向它的导出，
> 生成的模块一加载就报 `failed to grow table by 4`。构建脚本现在检测版本并跳过，
> 所以这里给的是未优化体积；binaryen ≥ 116 下 `-O3` 仍可用。
